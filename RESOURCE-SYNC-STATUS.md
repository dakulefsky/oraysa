# Official Oraysa PDF sync

## Intended behavior

- On plugin startup, if the user has already approved a persistent folder, check all five new amudim in the current Oraysa week.
- Repeat the check every six hours while the plugin is open and when the device reports that it has come online.
- Download only PDF links discovered on Oraysa's own daf pages, and only from `www.oraysa.org` or `oraysa-media.s3.amazonaws.com`.
- Keep downloaded files on the user's device. Do not automatically remove previous weeks.
- Let the user request an older learning date separately.
- Check ETag / Last-Modified / Content-Length before replacing a previously downloaded file.
- Do not download audio, video, or third-party content. Do not generate any learning material.

## Otzaria requirements

The manifest declares `network.access`, `fs.user_files.read`, and `app.info.read`, plus both Oraysa URL prefixes.

The Otzaria maintainer allowlist is separate from the plugin manifest. These two prefixes still need to be added to `plugin_network_allowlist.txt` in the Otzaria repository:

- `https://www.oraysa.org`
- `https://oraysa-media.s3.amazonaws.com`

Without that upstream allowlist approval, Otzaria will reject the requests even though the plugin declares them.

## Catalog discovery verification still required

The resource adapter currently fetches the existing per-daf URL generated by `OraysaCore.siteUrl()` and extracts PDF links from the returned HTML / embedded page data. The supplied Yevamos S3 PDF proves direct object access, but it does not by itself prove that the per-daf page returns a machine-readable list of all official PDFs.

Before release, run the plugin inside Otzaria with network access approved and verify that the Yevamos 120b–122b *Pisgamei Oraysa – Marei Mekomos* PDF is discovered from the relevant daf page. If Oraysa serves the catalog through a separate JSON/API request or JavaScript-only component, replace the generic HTML extractor with that documented endpoint. Never infer S3 object names or enumerate the private bucket.

## Storage model

The user chooses a persistent folder once through `fs.pickUserFolder`. Downloads use `network.download` with a destination path inside that approved folder. The plugin keeps a URL-to-file metadata index in Otzaria plugin storage.

## Visual refresh (2026-11-01)

The interface received a styling-only refresh: Montserrat is the preferred display face for Latin-script headers, navigation labels, badges, and compact UI labels, with system sans-serif fallback. Hebrew text retains its readable Hebrew/system fallback rather than forcing a Latin typeface onto Hebrew glyphs. The palette is more restrained ivory, stone, and warm gold; cards, controls, focus states, spacing, and compact mobile navigation have been refined. No remote font dependency was added, so the actual Montserrat font file must be available on the host device for that face to render; otherwise the declared fallback is used. Functional behavior and official-resource restrictions are unchanged.


## Bundled display font (2026-11-01)

Montserrat is bundled locally as an unmodified variable TrueType font from Google Fonts under the SIL Open Font License 1.1. The complete upstream license is included at `fonts/OFL.txt`. The font is loaded from the plugin package with `font-display: swap`; no external font request is required. The display font stack falls back to Rubik for glyphs not present in Montserrat, preserving Hebrew UI rendering. Functional behavior and official-resource restrictions are unchanged.
